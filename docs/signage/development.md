# 개발 구조와 검증

## 워크스페이스

```text
저장소 루트                     Astro 사이트, 기사, 설정, 정적 데이터 생성
packages/signage-player         공용 React 화면, 검증, 순수 시간 계산
apps/signage-desktop            Electron 호스트, 로컬 캐시, 모니터 설정
docs/signage                    운영·설정·개발 문서
```

루트와 데스크톱 앱이 `@kmucs/signage-player`를 `workspace:*`로 참조한다. 공용 패키지의 코어는 TypeScript로 컴파일하고, React 화면은 각 앱의 Vite 빌드에서 묶는다. Electron API는 공용 패키지에 넣지 않는다.

| 명령 | 역할 |
| --- | --- |
| `pnpm dev` | 공용 코어 빌드 후 Astro 개발 서버 |
| `pnpm build` | 공용 코어와 기존 사이트, 정적 feed 빌드 |
| `pnpm signage:dev` | Electron 빌드·런타임 준비 후 모니터 설정 앱 실행 |
| `pnpm signage:demo` | 한 모니터에서 첫 세션의 목록·상세 창 2개 또는 3개로 개발 확인 |
| `pnpm signage:build` | 데스크톱 렌더러와 공용 코어 빌드 |
| `pnpm signage:dist` | Windows x64 NSIS 설치 파일 패키징 |
| `pnpm test:signage` | 시간 계산, 설정 검증, 캐시와 모니터 배정 테스트 |
| `pnpm check:signage` | 공용 패키지·데스크톱·웹 TypeScript 및 호스트 구문 검사 |
| `pnpm check:web` | Astro 콘텐츠 타입 생성과 웹 TS/TSX 타입 검사. Astro 템플릿 검사와는 별개 |

데스크톱 개발 명령은 빌드된 화면을 실행한다. 화면 코드를 바꿨으면 명령을 다시 실행한다. 공용 코어 수정 후 웹 개발 서버를 켜둔 상태라면 `pnpm --filter @kmucs/signage-player build`도 실행한다.

## 시간과 동기화

`core.ts`의 `frameAt`이 누적 재생 시간을 기준으로 기사 인덱스, 진행률, 전환 진행률을 계산한다. 타이머 콜백 횟수로 인덱스를 증가시키지 않는다. 따라서 창을 늦게 열거나 프레임을 놓쳐도 현재 시각의 위치로 돌아온다.

Electron 호스트는 시작 시 UTC 시각과 `performance.now()`를 연결한다. 실행 중에는 단조 증가 시간으로 진행한다. 각 렌더러는 IPC 시계 샘플 5개 중 왕복 시간이 가장 짧은 값을 사용해 호스트와의 차이를 계산한다. 매 30초 및 상태 수신 시 다시 보정한다. 시계 보정 외에 매 프레임 통신은 없다.

모션도 동일한 절대 진행률에서 계산한다. 단순 CSS transition 시작 시각에 의존하지 않으므로 창별 실행 시점 차이가 누적되지 않는다. `motion.ts`는 선택 표시의 가속·감속과 제목·사진·요약의 단계별 진행률을 계산한다. 이전 제목이 사라지기 전에 다음 제목이 겹치지 않도록 구간을 나누며, 이동에는 `transform`을 사용한다. 전환 중 상세 레이어는 최대 두 개이고 기사 ID를 키로 사용해 전환 종료 때 DOM을 다시 만들지 않는다. OS의 모션 감소 설정은 이동·페이드를 생략하되 기사 타임라인은 유지한다.

절전 복귀 시 호스트 기준을 현재 UTC로 다시 맞춘다. 재시작 시 디스크의 재생 기준으로 현재 위치를 계산한다. Windows 시각이 잘못되면 재시작 위치가 달라질 수 있으므로 Windows 자동 시각 설정을 유지한다. 서로 다른 PC의 정밀 동기화는 이 구현의 보장 범위가 아니다.

주사율·GPU·화면 스캔 시점이 달라 물리적인 프레임 일치는 보장하지 않는다. 실제 장비의 검수 목표는 기사 전환 차이 100ms 이내다. 이는 실측 전의 목표이며 보장값이 아니다.

## 새 버전 준비와 적용

1. 호스트가 feed를 받아 schemaVersion과 필드를 검증한다.
2. 각 이미지와 폰트의 SHA-256을 확인하며 로컬에 저장한다.
3. 모든 실행 창이 새 이미지 디코딩과 글꼴 로딩을 마친 뒤 준비 완료를 전달한다.
4. 호스트가 세션별 다음 반복 경계와 새 기준 시각을 정해 저장하고 모든 창에 보낸다.
5. 각 창이 같은 시각에 `pending` 데이터를 선택한다. 호스트는 적용이 끝난 대기 상태를 정리한다.

현재 재생과 대기 버전을 함께 저장하므로 전환 전에 앱이 종료돼도 재시작 시 올바른 버전을 선택한다. 준비 중 오류가 발생하면 이전 버전이 계속 재생된다. 프레임 생성은 외부 서버 상태에 의존하지 않는다.

## 보안과 저장 경계

- 실행 코드는 앱에 포함한다. 원격에서는 JSON과 이미지·폰트만 가져온다.
- sandbox와 contextIsolation을 켜고 nodeIntegration은 끈다. `webSecurity`를 끄지 않는다.
- preload에는 필요한 IPC만 노출하며 호스트에서 호출 창과 메인 프레임을 검증한다.
- 설정 저장과 종료는 설정 창에서만 요청할 수 있다.
- 새 창, 외부 탐색, 권한 요청을 차단한다. 기사 원문은 QR로 연결한다.
- `signage://app` 로컬 프로토콜로 빌드된 화면과 허용된 해시 에셋을 제공한다. 경로 이동을 차단하고 CSP를 적용한다.
- feed는 최대 5MiB, 각 이미지·폰트는 최대 25MiB이며 다운로드 타임아웃은 30초다. 리다이렉트는 거절한다.
- 콘텐츠·설정 검증 실패와 파일 손상은 기존 재생 데이터를 덮어쓰지 않는다.

## 배포와 호환성

기존 `deploy.yml`은 사이트 빌드와 사이니지 테스트 후 GitHub Pages에 배포한다. pnpm 버전은 루트 packageManager와 워크플로에서 10.33.3으로 맞춘다. Windows 설치 파일은 별도 `signage-windows.yml`에서 생성한다. 앱 버전과 일치하는 `signage-v*` 태그를 푸시하면 검증과 빌드 완료 후 GitHub Release에 설치 파일, `.exe.blockmap`, `latest.yml`과 SHA-256 해시를 게시한다. electron-builder의 자체 게시는 끄고 릴리스 작업에서만 게시한다. `main` 수동 실행은 아티팩트만 생성한다. 자세한 절차는 [설치와 운영](./operations.md#설치-파일-만들기)을 참고한다.

`schemaVersion`은 원격 데이터 형식의 호환성을 나타내고 `revision`은 콘텐츠 버전을 나타낸다. 새로운 필드가 필수가 되거나 기존 의미가 바뀌면 구버전 앱에서 읽을 수 있는지 먼저 검토한다. 호환되지 않으면 schemaVersion과 앱 버전을 올리고, 앱 설치를 먼저 완료한 뒤 데이터를 전환한다.

`src/lib/signage.ts`와 `packages/signage-player/src/core.ts`가 데이터를 만들고 검증한다. 설정 구조를 바꿀 때는 두 코드, 테스트, `configuration.md` 예시를 함께 갱신한다. 현재 호스팅은 루트 경로(`/`)를 기준으로 한다. 서브디렉토리 호스팅으로 옮길 때는 preview의 feed·asset URL과 데이터 생성 경로도 함께 수정한다.

## 검증 기록

2026-10-10 개발 환경 기준:

- 공용 코어·리소스 수명 자동 테스트 16개, 데스크톱 저장·배정 테스트 7개 통과.
- `pnpm check:signage`, 기존 Astro 사이트 빌드, Electron 렌더러 빌드 통과.
- Chrome에서 현재 6개 기사 모두 목록·상세 기사 ID 일치와 텍스트 영역 넘침 없음 확인.
- macOS Electron 실제 창 2개에서 정상 실행, 새 revision의 반복 경계 적용, 목록·상세 기사 일치 확인.
- 1·2·3·4·5·6·7·13개 기사에서 첫·마지막 기사의 목록·상세 일치, 텍스트 영역 넘침과 화살표 위치 확인. 상세 화면 QR 1개와 사진 cover 크롭 확인.
- 테스트 HTTP 서버를 종료한 뒤 Electron을 다시 실행해 두 창 모두 마지막 revision으로 오프라인 복구 확인.
- electron-builder로 Windows x64 NSIS 설치 파일 생성 성공. 실제 Windows에서 설치·실행한 결과는 아님.
- 모션 개선 버전 1.0.2: 0.95초 전환을 30fps의 시각 단계로 렌더링해 목록·상세 기사 일치, 제목 겹침 없음, 사진 위치 고정, 상세 레이어 최대 2개, 같은 페이지 반복 시 목록 유지, 모션 감소 설정의 즉시 표시를 확인. 미리보기 영상은 `apps/signage-desktop/release/motion-preview.mp4`.
- Windows의 실제 모니터, 자동 로그인 후 실행, 8시간 연속 재생, 케이블 분리·재연결은 현장 검증 필요.

자동 테스트의 8시간 시각 계산은 실제 8시간 동안 앱을 실행한 시험과 다르다. 개발 환경에는 기존 vanilla-extract 플러그인의 Vite peer dependency 경고가 있으나 현재 사이트 빌드는 통과했다.

## 수개월 연속 운영과 메모리 검사

2026-10-10 점검에서 갱신할 때마다 등록하던 `FontFace`, 로딩 완료 revision Set, 배정하지 않은 삭제 세션의 누적 보관을 수정했다. `AssetCache`는 현재·대기·준비 중 버전만 보유하며 이전 글꼴을 `document.fonts.delete()`로 제거한다. 내용만 바뀐 버전은 글꼴 파일의 SHA-256을 기준으로 기존 글꼴을 공유한다. 참조가 없는 글꼴만 제거한다. 중복 준비 요청은 같은 Promise를 공유한다. 준비 실패, 화면 해제, 준비 취소 시 리소스를 정리한다. 부분적으로 로딩한 글꼴은 두 글꼴이 모두 성공하기 전에는 등록하지 않는다.

이미지는 한 번에 하나씩 사전 디코딩해 순간적인 부하를 줄인다. 이미 확인한 이미지의 SHA-256은 현재 필요한 버전에 한해 기억하며, 내용이 같으면 다시 디코딩하지 않는다. 준비 제한은 30초다. 다운로드를 헤더 검사에서 거절할 때도 응답 스트림을 취소한다. 호스트의 정리 작업은 한 번에 하나만 실행하고, 캐시 정리 중에는 다운로드를 시작하지 않는다. 실패한 버전의 남은 파일과 임시 파일도 정리한다. 모니터 배정이 유지된 삭제 세션은 의도적으로 보존한다.

`requestAnimationFrame`, `ResizeObserver`, 미디어 쿼리 이벤트, IPC 구독과 시계 보정 타이머는 화면 해제 시 해제한다. 재생 이력이나 프레임을 배열에 쌓지 않는다. 매일 재시작하는 방식으로 누수를 가리지 않는다.

### 실제 측정 결과

메모리 수정 버전 1.0.1을 macOS, Electron 44.7.0에서 20회 갱신과 추가 1분 재생, 총 261.9초 실행했다. 작은 실제 창 두 개와 설정 창 하나를 사용했다. 이미지 내용과 미배정 세션 ID를 계속 바꿨다.

| 항목 | 워밍업 후 | 종료 시 |
| --- | --- | --- |
| 목록 화면 GC 후 JS 힙 | 3.60MiB | 3.71MiB |
| 상세 화면 GC 후 JS 힙 | 3.55MiB | 3.73MiB |
| 전체 Electron 프로세스 작업 집합 합계 | 856.4MiB | 703.8MiB |
| 등록 글꼴 | 창마다 2개 | 창마다 2개 |

| 이벤트 리스너 | 목록 177개, 상세 175개 | 동일 |
| 디스크 에셋 | 10개 | 10개 |

검사 기준을 통과했다. 앞선 중간 구현에서는 반복 이미지 디코딩 때문에 프로세스 작업 집합 증가 기준을 넘겨 실패했으며, 동일 해시 이미지의 중복 디코딩을 제거한 뒤 다시 측정한 결과다. JS 힙만 보고 통과로 판단하지 않았다. 측정 원본은 `apps/signage-desktop/release/memory-check.jsonl`에 있다. 이 결과는 몇 분의 갱신 부하 검사이며 수개월 연속 실행의 보증은 아니다.

```sh
pnpm --filter @kmucs/signage-desktop test:memory
```

GUI가 있는 개발 PC에서 실행한다. 이미 실행 중인 개발용 KMUCS 앱은 종료한다. 테스트는 임시 로컬 서버와 별도의 앱 데이터 폴더를 사용하며, 저장소의 운영 설정이나 기존 앱 캐시는 수정하지 않는다. 목록·상세 창 두 개에서 5초짜리 기사 두 개를 반복하며 20회 갱신한다. 매번 이미지 파일 내용과 미배정 세션 ID도 바꿔 과거 버전의 정리를 확인한다. 재생 시간 자체를 가속하지 않는다.

`apps/signage-desktop/release/memory-check.jsonl`에 각 샘플을 저장한다. 이 파일은 다음 실행 때 덮어쓰므로 보관할 결과는 별도로 복사한다. 측정 항목:

- 렌더러의 GC 후 JS 힙, DOM 노드·문서·이벤트 리스너 수, 등록 글꼴 수.
- 호스트의 JS 힙·외부 버퍼·RSS와 Electron 각 프로세스의 작업 집합 크기.
- 재생 창 수, 호스트의 screen·IPC 리스너 수, 디스크 에셋 파일 수.

자동 실패 조건은 글꼴 두 개 초과, 창 세 개 이외, 과거 에셋·세션 잔존, 오류 발생, 워밍업 후 렌더러 JS 힙 8MiB 초과 증가, DOM 30개 초과 증가, 이벤트 리스너 10개 초과 증가, 전체 프로세스 작업 집합의 256MiB 초과 증가다. 이는 회귀 탐지 기준이며 메모리 사용량 보장치가 아니다. 프로세스 작업 집합 크기는 Chromium 캐시와 GPU 때문에 JS 힙과 다를 수 있으므로 결과의 추세도 검토한다.

48시간 반복 재생 측정은 다음과 같다. 20회 갱신 후 추가 2,880분 동안 1분 간격으로 기록한다. 화면·절전 설정을 실제 운영과 같게 맞춘다.

```sh
pnpm --filter @kmucs/signage-desktop test:memory --updates 20 --idle-minutes 2880
```

이 검사는 실제 Electron 창을 사용하지만 개발 모드의 작은 창 두 개다. Windows 전체 화면 4개, 실제 이미지 크기와 GPU 드라이버의 장기 동작은 별도 현장 검수가 필요하다. 최소 48시간, 가능하면 7일 동안 작업 관리자에서 앱의 모든 자식 프로세스 메모리도 기록한다. 초기 캐시가 채워진 이후에도 같은 콘텐츠에서 계속 증가하면 정상으로 판정하지 않는다. 몇 분의 반복 갱신 검사나 순수 시각 계산으로 수개월 무누수를 보장할 수 없다.

관련 API: [FontFaceSet.delete](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/delete), [Electron app.getAppMetrics](https://www.electronjs.org/docs/latest/api/app#appgetappmetrics).


### 1.0.4 편성 도구 검증

- `/signage/setup/`에서 공개 기사 21개를 읽고 현재 편성 밖의 기사를 검색·추가하는 흐름을 확인했다.
- 6개 기사 2대 → 4대(3+3) → 2대(6) 전환, 7개 기사 4대(4+3) 편성, 개별 재생시간 변경과 순서 이동을 확인했다.
- A·B 미리보기에서 세션 전환과 화면 표시를 확인했다. 새 편성은 운영 피드를 폴링하지 않는다. 미리보기를 교체하면 기존 타이머·에셋을 해제한다.
- 브라우저에서 내보낸 JSON의 2개 세션, 6개 기사 ID와 재생시간을 확인했다. 사이트 설정 파일 자체는 바꾸지 않았다.
- 기사 분배, 다른 세션 보존, 입력 변조 방지, 모니터 빠른 배정 테스트 4개를 추가했다. 전체 사이니지 테스트 27개 통과.
- 공유 플레이어·Electron 타입 검사 및 새 웹 편성 파일에 대한 Astro 타입 포함 검사 통과. 루트 `tsc --noEmit`은 기존 Astro 생성 타입 포함 설정과 NewsletterBuilder의 Window.ResizeObserver 타입 오류가 있어 전체 프로젝트 통과로 보고하지 않는다.
- Windows 실제 4모니터 연결과 장시간 연속 운영은 별도 현장 확인이 필요하다. 이전 메모리 실측을 새 버전의 수개월 무누수 보장으로 해석하지 않는다.


### 1.1.0 상세 화면 2개와 배치 검증

- 3대 구성은 목록 1개와 상세 2개를 사용한다. `frameAt`이 두 기사 인덱스와 공통 진행률을 계산하고, 두 기사 중 더 긴 시간을 사용한다. 홀수 개의 마지막 묶음은 마지막 기사와 첫 기사다.
- `schemaVersion: 2`와 `detailCount: 2`를 도입했다. 앱 1.1.0은 기존 버전 1도 읽는다. 구버전 앱은 버전 2를 거절하므로 앱을 먼저 업그레이드하고 사이트 설정을 배포한다.
- 기사 수 1~100개에 대해 페이지당 최대 6개, 중복 없는 목록, 두 강조 기사의 가시성, 반복 경계와 시간 계산을 검사했다. 모니터 역할 누락과 잘못된 스키마도 검사했다. 전체 사이니지 테스트 32개 통과.
- 브라우저에서 21개 기사 전체를 3대 미리보기로 확인했다. 마지막 21·1 묶음도 목록과 상세가 일치하고 제목·요약 넘침이 없었다.
- 1·2·3개 목록은 사진이 0개이고 높이가 각각 320·654·988px이며 아래 공간을 비운다. 카드 넘침이 없었다. 상세 제목·사진 위치는 고정하고 요약은 위쪽 정렬, 글자 수에 따라 30·33·36px로 표시한다.
- 편성 도구의 일반 문단 스타일이 미리보기 요약 글꼴까지 줄이던 문제를 수정했다. 실제 렌더링 크기와 두 상세 화면의 사진 시작 위치가 일치함을 확인했다.
- 공유 플레이어·앱·웹 편성 관련 타입 검사와 사이트·데스크톱 빌드 통과. 미리보기 교체 후 등록 글꼴은 2개를 유지했다. 새 타이머나 지속적인 재생 이력 저장은 추가하지 않았다.
- Windows 실제 3모니터 연결, 수개월 연속 실행은 검증하지 않았다. 1.0.1의 짧은 메모리 실측은 이번 버전의 장기 무누수 보장이 아니다.


### 1.1.1 홀수 묶음과 카드 크기 검증

- 홀수 개의 마지막 묶음은 마지막 두 기사다. 7개는 1·2 → 3·4 → 5·6 → 6·7이며, 마지막 묶음의 시간도 6번과 7번 중 긴 시간을 사용한다. 첫 기사 시간에 영향을 받지 않는다.
- 목록은 다른 페이지의 기사를 복제하지 않는다. 7개는 4+3, 13개는 6+4+3으로 나눠 마지막 두 기사를 같은 페이지에 유지한다. 단일 상세 구성에도 동일한 페이지 분할을 적용한다.
- 1~5개 카드는 5개 기준의 동일한 높이(세로 FHD에서 약 281px), 6개일 때만 약 231px로 줄인다. 사진 없이 위쪽부터 배치하고 아래 여백을 남긴다. 선택 테두리도 같은 높이 계산을 사용한다.
- 상세 제목 영역과 사진 사이 28px, 사진과 요약 사이 36px로 조정했다. 기사마다 사진 위치가 같고 요약은 위쪽에 정렬한다.
- 1~100개 기사의 페이지 누락·중복, 마지막 묶음 시간과 반복 경계를 검사했다. 전체 테스트 34개, 공유 플레이어·앱·웹 편성 타입 검사, 사이트·데스크톱 빌드를 통과했다.
- 브라우저에서 1~6개 카드의 실제 크기, 7개 전체 순서, 공개 기사 21개의 텍스트 넘침을 확인했다. 새 타이머·캐시·이력 저장을 추가하지 않았다.
- 이 변경은 화면과 타임라인 코드이므로 기존 Windows 앱에는 1.1.1 설치가 필요하다. 이후 기사·설정 변경은 기존 사이트 폴링 방식으로 적용한다. Windows 실기와 장시간 연속 실행은 이번에 검사하지 않았다.


### 1.2.0 뉴스레터 원문 요약과 폰트 맞춤

- 요약은 공개 HTML 뉴스레터의 기사 링크 안 `<p>`에서 빌드 시 추출한다. 기존 HTML 파서 parse5를 직접 의존성으로 등록했다. 엔티티와 문단 구분을 보존하며 문장을 다시 쓰거나 잘라내지 않는다. Windows에서 HTML을 실행하거나 별도 크롤링하지 않는다.
- 세션에서 지정한 뉴스레터를 우선하고, 해당 기사가 없으면 가장 최근 공개 HTML 뉴스레터, 기사 대체 요약 순으로 사용한다. 편성 미리보기와 실제 feed에 같은 규칙을 적용한다.
- 데이터 버전 3은 1~4문단, 합계 800자까지 허용한다. 앱 1.2.0은 버전 1·2도 읽는다. 긴 요약을 지원하지 않는 구버전 앱이 잘못 표시하지 않도록 앱을 먼저 업그레이드하고 새 데이터를 배포한다.
- 상세 요약은 최대 30·33·36px에서 시작해 실제 본문 영역에 맞도록 최소 16px까지 폰트만 줄인다. 문단은 모두 유지한다. 측정은 기사/요약이 바뀔 때만 수행하며 매 프레임 측정하거나 타이머·Observer를 추가하지 않는다.
- 게시된 3호 페이지와 브라우저에서 직접 대조했다. 6개 요약이 문단별로 완전히 일치하며 499~599자 전체가 23~25px로 표시됐다. 상세 본문 넘침이 없고 사진 시작 위치는 두 화면 모두 같았다. 글꼴 등록은 2개를 유지했다.
- 추출·엔티티·중복 검사, 실제 3호 요약 추출, 긴 요약 버전 검증과 편성 미리보기의 호수별 요약 선택을 검사했다. 전체 테스트 38개 통과. 공유 플레이어·앱·관련 웹 파일 타입 검사와 사이트·데스크톱 빌드 통과. 생성 feed의 6개 요약도 소스 추출 결과와 정확히 일치했다.
- Windows 실제 화면과 장시간 메모리 측정은 이번에 실행하지 않았다. 기존 짧은 메모리 검사 결과로 장기간 무누수를 보장하지 않는다.


### 뉴스레터 요약이 있는 기사만 편성

- 편성 카탈로그와 재생 feed 모두 공개 HTML 뉴스레터 요약이 있는 기사만 포함한다. 기사 소개와 `displaySummary`를 상세 요약으로 대체하던 처리를 제거했다.
- 기존 설정의 기사라도 뉴스레터 요약이 없으면 재생 대상에서 제외한다. 남는 기사가 없는 세션은 빌드를 중단해 빈 편성을 배포하지 않는다. 잘못된 기사 ID는 기존대로 오류다.
- 제목·이미지만 있는 기사와 공백 문단은 요약이 있는 것으로 취급하지 않는다. 현재 공개 기사 21개 중 1~3호 요약이 있는 16개가 편성 화면에 표시되고, 요약이 없는 5개는 제외된다.
- 이 변경은 사이트의 데이터 생성과 편성 페이지에만 적용된다. Windows 앱 1.2.0 재설치는 필요 없으며 사이트 배포 후 새 데이터를 받는다.

### 1.2.1 월호 호환 및 요약 없는 기사 제외

- 숫자 호수에는 기존 `Vol. 003` 표시를 유지하고, `9월호` 같은 문자열은 그대로 표시한다. 공유 플레이어, 뉴스레터 생성기의 이메일·표지·메타데이터, 목록 이미지 도구에 동일한 표시 함수를 적용했다.

- 뉴스 페이지는 기존부터 문자열 ID와 제목을 지원하며 `publishedAt`으로 정렬한다. 데이터 형식과 Windows 재생 프로토콜 변경은 없다. 1.2.1을 처음 한 번 설치하면 이후 월호 교체도 사이트 배포와 기존 폴링으로 반영한다.
- 요약 필터는 사이트 빌드에서만 수행한다. 기존 앱 1.2.0도 필터링된 피드를 수신할 수 있다. 현재 21개 공개 기사 중 뉴스레터 요약이 있는 16개만 편성 도구에 표시된다.

- 브라우저의 월호 예시에서 등록 커맨드를 생성해 5개 요약이 정상 추출되는지 확인했다. 운영 설정은 기존 3호로 유지했고 생성 피드의 6개 요약이 원문과 동일함을 확인했다.
- Windows 1.2.1 NSIS 설치 파일(약 106.9MiB)을 생성하고 ASAR의 버전과 JS·CSS가 최신 빌드와 일치함을 확인했다. 설치 파일은 코드 서명되지 않았다. 실제 Windows 설치·다중 모니터·장기 연속 실행은 이번 작업에서 검증하지 않았다.
- 월호는 발행 단위이며 접근 권한이 아니다. 학내 수신자에게만 배포하더라도 사이트의 뉴스 페이지와 사이니지 피드는 공개 URL이다.

- 사용하지 않는 `displaySummary` 스키마·타입·6개 기사 필드를 제거했다. 상세 요약의 원본은 뉴스레터 HTML 한 곳으로 유지한다. 기사 본문과 최근 추가된 iCar 요약은 수정하지 않았다.
- 뉴스레터 추출 테스트가 실제 3호의 기사 수를 6개로 고정해 정상적인 기사 추가에도 실패하던 문제를 수정했다. 원문 보존과 수정 반영은 독립된 긴 요약 예제로 검사하며, 실제 발행 콘텐츠는 빌드 결과와 대조한다.
- `.astro/types.d.ts`와 `astro/client` 타입을 프로젝트에 연결했다. 임시 외부 설정 없이 `pnpm check:web`으로 웹 전체 TS/TSX를 검사하고, 기존 CI의 `pnpm check:signage`에도 포함했다. 이 명령은 Astro 템플릿 자체의 타입 검사와는 별개다.
- 테스트 42개, 웹·공용 플레이어·앱 타입 검사, 사이트·데스크톱 빌드 통과. 현재 3호 7개 기사 모두 뉴스레터에서 자동 편성되며 요약 원문과 이미지·글꼴 해시가 일치한다. 사이트맵에서 사이니지 경로 제외도 확인했다.
- 브라우저에서 요약이 있는 전체 17개 기사를 3대 미리보기로 확인했다. 제목·목록 소개·요약 넘침이 없고, 요약 폰트는 23~27px였다. 현재 3호 마지막 묶음은 6·7번이고 두 상세 요약은 25px·24px로 표시됐다.
- 기존 1.2.1 Windows 설치 파일의 ASAR 버전과 호스트·preload·저장 모듈·렌더러 JS/CSS가 현재 코드와 일치한다. 이번 정리는 설치 앱의 실행 코드를 변경하지 않아 재패키징하지 않았다.
- 메모리 검사 도구의 로컬 서버 시작 실패를 처리해, 오류가 나도 임시 폴더 정리 경로를 통과하도록 보완했다.

최종 메모리 실측: macOS / Electron 44.7.0 / 앱 1.2.1에서 콘텐츠 20회 갱신과 추가 1분 재생, 총 261.9초를 실행해 PASS했다. 워밍업 후 GC 기준 목록·상세 JS 힙은 3.58 / 3.59MiB에서 3.68 / 3.77MiB로 변했다. DOM은 104 / 81개, 이벤트 리스너는 173 / 175개, 등록 글꼴은 각 2개로 유지됐다. 창 3개, 디스크 캐시 11개, 호스트 screen 리스너 3개와 IPC 리스너 1개도 유지됐다. 전체 작업 집합은 791.8MiB에서 736.0MiB였다. 검사 오류는 없었다. 원본은 무시된 빌드 출력 폴더의 `apps/signage-desktop/release/memory-check-1.2.1-final.jsonl`에 별도 보관했다.

이 결과는 약 4분의 갱신 부하 검사다. 운영 배포, 실제 Windows 설치·전체 화면 다중 모니터 및 48시간 이상 장기 실행 검증은 수행하지 않았다. 수개월 무누수를 보장하는 결과로 해석하지 않는다.

## 1.2.2: Windows 작업표시줄과 목록 분할

- Windows 재생 창을 `pop-up-menu` 수준의 항상 위 창으로 지정했다. 전체 화면이어도 포커스가 없는 모니터에 작업표시줄이 남는 상황을 보완한다. 설정 창은 그 위로 표시하며 새 재생 창이 나타날 때 설정 창이 가려지지 않게 한다. OS 작업표시줄 설정 변경이나 주기적인 포커스 강제 이동은 사용하지 않는다.
- 목록은 앞 페이지부터 채우고 마지막 한 개만 남을 때 한 기사를 옮긴다. 7개는 5+2, 8개는 6+2, 13개는 6+5+2다. 페이지 사이 기사는 중복하지 않는다.
- 상세 두 화면은 같은 목록 페이지 안의 기사만 표시한다. 7개에서 1·2, 3·4, 4·5, 6·7로 진행하며 각 묶음의 긴 재생시간을 사용한다. 기사 미리보기 이동도 해당 기사가 실제로 포함된 묶음으로 맞췄다.
- 테스트 43개, 타입 검사, 사이트와 앱 빌드 통과. 1~100개에서 목록 누락·중복, 상세 두 기사 가시성, 페이지 번호와 반복 경계를 확인했다. 브라우저에서 7개 목록의 1~5와 6~7 표시를 확인했다.
- macOS Electron 갱신 4회, 41.9초 회귀 검사 PASS. 워밍업 후 목록·상세 JS 힙은 3.55 / 3.61MiB에서 3.55 / 3.63MiB였고 DOM 104 / 81개, 리스너 173 / 175개, 창 3개와 캐시 11개가 유지됐다. 장기 실행이나 Windows 창 순서 검증을 대신하는 검사는 아니다.
- 실제 Windows 다중 모니터의 작업표시줄 가림과 설정 창 접근은 현장 확인이 필요하다. 앱 1.2.2를 설치해야 적용되며 사이트 콘텐츠 갱신만으로 기존 실행 파일의 창 정책은 바뀌지 않는다.

## 1.2.3: 앱 이름과 국민대학교 아이콘

- 표시 이름, 창 제목, 설정 화면과 릴리스 이름을 요청한 철자 `KMUCS News Sinage`로 통일했다. 설치 파일은 `KMUCS.News.Sinage.Setup.<버전>.exe`다.
- `public/images/logo.svg`의 국민대학교 원형 로고를 512×512 PNG로 변환한 `apps/signage-desktop/assets/icon.png`를 사용한다. 로고 도형과 색상을 유지하며 새 디자인으로 생성하지 않는다. electron-builder가 Windows 아이콘 형식으로 변환하고, 창 아이콘과 설정 화면도 같은 이미지를 사용한다.
- 앱 ID는 `kr.ac.kookmin.cs.signage`, 운영 저장 폴더는 `KMUCS Signage`를 유지한다. 개발용 임시 폴더를 포함한 저장 경로를 단일 인스턴스 잠금 전에 지정한다. 저장된 자동 실행 선택은 새 실행 파일 경로로 갱신한다.
- 테스트 43개와 타입 검사, 앱 빌드 통과. macOS Electron을 실제 실행해 새 내부 이름, 임시 저장 경로, 기존 설정 파일 읽기와 로고 로딩을 확인했고 콘텐츠 갱신 2회 검사(21.8초)가 통과했다. Windows 기존 설치본의 업그레이드 및 자동 로그인 실행은 현장 확인이 필요하다.

## 1.3.0: 앱 내 업데이트

- `electron-updater`의 GitHub/NSIS 경로를 사용한다. 설치된 Windows 앱만 시작 시와 6시간마다 최신 정식 릴리스를 확인하며, 설정 창에서 다운로드와 설치를 직접 시작한다. 자동 다운로드·종료 시 자동 설치·다운그레이드·프리릴리스는 사용하지 않는다. 기존 1.2.3 이하 앱에는 이 기능이 없어 1.3.0을 한 번 직접 설치해야 한다.
- `src/updates.mjs`는 상태와 중복 실행 방지만 관리한다. 다운로드·SHA-512 검사·설치 실행·캐시는 라이브러리에 맡긴다. 기본 서명 검증은 끄지 않으며, 현재 인증서가 없어 배포자 신원 검증과 SmartScreen 평판은 확보되지 않았다.
- 업데이트 IPC는 기존 설정 창의 메인 프레임만 호출할 수 있다. 렌더러가 임의 다운로드 주소나 실행 파일 경로를 전달할 수 없다. 설치 전 재생 상태를 저장하고, 기존 종료 처리로 재생 창을 닫는다. 모니터 배정과 캐시 저장 경로는 유지한다.
- 별도 주기 타이머를 만들지 않고 기존 유지 관리 루프를 사용한다. 이벤트 리스너는 앱 시작 때 한 번 등록하며, 다운로드 진행은 정수 백분율이 바뀔 때 설정 창에만 전송한다. 네트워크·다운로드 오류는 현재 뉴스 재생을 중단하지 않는다.
- 릴리스에는 `.exe`, `.exe.blockmap`, `latest.yml`, `SHA256SUMS.txt`를 함께 게시한다. 저장소의 최신 정식 릴리스에 업데이트 목록이 있어야 한다. 빌드의 GitHub 게시 설정이 설치 앱의 `app-update.yml`을 생성하며, 실제 게시는 기존 CI 릴리스 작업이 담당한다.
- 테스트 46개, 웹·공유 플레이어·앱 타입 검사, 사이트·앱 빌드 통과. 업데이트 테스트는 수동 설치, 중복 요청, 네트워크 오류와 재시도, 검증 실패 시 설치 금지, 1,000회 확인 후 리스너 수 유지를 검사한다.
- macOS Electron에서 개발 모드의 업데이트 비활성화와 IPC 거절을 확인하고 콘텐츠 갱신 4회, 41.9초 회귀 검사에 통과했다. 워밍업 후 목록·상세 JS 힙은 3.57 / 3.59MiB에서 3.58 / 3.60MiB로 변했고 DOM 104 / 81개, 리스너 173 / 175개, 창 3개와 캐시 11개가 유지됐다. 이 검사는 실제 Windows 업데이트 실행이나 장기 무누수 검증을 대신하지 않는다.
- Windows CI [38044999893](https://github.com/kookmin-sw/newsletter/actions/runs/38044999893)에서 검증·패키징·게시가 완료됐다. 공개 1.3.0 설치 파일(112,679,750바이트)과 업데이트 파일들의 SHA-256 및 `latest.yml`의 SHA-512·크기 일치를 확인했다. 실제 `electron-updater`를 macOS Electron에서 Windows 채널로 실행해 1.2.3 기준 새 버전 발견, 전체 설치 파일 다운로드·검증, `ready` 상태까지 확인했다. 설치 파일 실행과 Windows 차등 다운로드는 이 검사에 포함하지 않았다.
- 실제 Windows 설치·업데이트 재시작·SmartScreen 동작과 수개월 연속 실행은 현장 검증이 필요하다. 자동 업데이트로 Windows 보안 경고를 없앤다고 보장하지 않는다.
